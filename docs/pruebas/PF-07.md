# Prueba Funcional PF-07 — Control atómico de cupo bajo concurrencia simultánea

- **Identificador:** PF-07
- **Épica origen:** E5 — Inscripciones y control de cupos
- **Requisitos asociados:** RF-16, CA-04, RNF-04, RN-04, RN-05
- **Responsable:** Integrante B
- **Herramienta utilizada:** Prueba de concurrencia real con hilos (`concurrent.futures.ThreadPoolExecutor`), SQLite en archivo temporal con modo WAL y `PRAGMA busy_timeout=5000` en `tests/test_inscripciones.py`
- **Estado actual:** Ejecutada y aprobada en E5 (cero sobrecupos bajo contención extrema)

## Condiciones iniciales

1. Base de datos SQLite configurada en archivo físico temporal con `journal_mode=WAL` y `busy_timeout=5000` por conexión, permitiendo múltiples conexiones concurrentes sin bloqueo fatal.
2. Un evento publicado con capacidad limitada fijada: `cupo_maximo = 5`.
3. 20 usuarios participantes ficticios distintos generados en la base de datos, cada uno con sesión autenticada independiente.
4. Piscina de hilos (`ThreadPoolExecutor(max_workers=10)`) configurada para disparar solicitudes HTTP concurrentes hacia el endpoint de inscripción.

## Casos cubiertos en E5

### Caso PF-07.1 — Disputa de 5 cupos por 20 participantes simultáneos (`CA-04`, `RNF-04`)
- **Método / Ruta:** `POST /api/v1/eventos/{evento_id}/inscripciones`
- **Mecanismo de contención:** Cada hilo invoca la API para un participante diferente contra el mismo evento.
- **Transaccionalidad en servidor:**
  - La transacción de inscripción ejecuta **`BEGIN IMMEDIATE`** para adquirir bloqueo reservado en SQLite.
  - Inserción condicional SQL verificando que las inscripciones activas sean estrictamente menores al `cupo_maximo`:
    ```sql
    INSERT INTO inscripciones (evento_id, participante_id, estado, creado_en)
    SELECT :evento_id, :participante_id, 'activa', :ts
    WHERE (
        SELECT COUNT(*) FROM inscripciones
        WHERE evento_id = :evento_id AND estado = 'activa'
    ) < (SELECT cupo_maximo FROM eventos WHERE id = :evento_id);
    ```
  - Si `rowcount == 0`, se efectúa rollback y se lanza `Conflicto(CUPO_AGOTADO)`.
  - Índice único parcial `ux_inscripciones_activa` para prevenir duplicados concurrentes.
- **Pasos:**
  1. Lanzar los 20 hilos simultáneamente mediante `executor.map`.
  2. Recolectar los códigos de estado HTTP y respuestas de cada hilo.
  3. Contar en base de datos las filas efectivas en la tabla `inscripciones` con `estado = 'activa'`.
  4. Consultar `GET /api/v1/catalogo/eventos/{id}` para verificar disponibilidad final.
- **Resultado esperado:**
  - Exactamente **5 solicitudes exitosas** con HTTP **201 Created**.
  - Exactamente **15 solicitudes rechazadas** con HTTP **409 Conflict** (`error.codigo == "CUPO_AGOTADO"`).
  - Cero errores de colisión no controlada (sin HTTP 500 ni bloqueos perpetuos).
  - La base de datos contiene exactamente **5 registros activos**, `cupos_disponibles == 0` y **ningún sobrecupo** (Principio IV de la constitución).
- **Resultado obtenido:** Exactamente 5 respuestas 201 y 15 respuestas 409 confirmadas en `tests/test_inscripciones.py::test_concurrencia_hilos_sin_sobrecupo`.
- **Estado:** Aprobada.

### Caso PF-07.2 — Dos solicitudes simultáneas disputando el último cupo (`cupo = 1`)
- **Método / Ruta:** `POST /api/v1/eventos/{evento_id}/inscripciones`
- **Datos de entrada:** Evento publicado con `cupo_maximo = 1` y dos participantes enviando petición en el mismo instante.
- **Resultado esperado:**
  - Exactamente **1 participante obtiene el cupo** (HTTP 201).
  - Exactamente **1 participante es rechazado** con HTTP 409 (`CUPO_AGOTADO`).
  - Total de inscritos activos en BD = 1.
- **Resultado obtenido:** Verificado exitosamente sin sobrecupos.
- **Estado:** Aprobada.
