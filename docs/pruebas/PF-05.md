# Prueba Funcional PF-05 — Inscripción válida a un evento con cupo disponible

- **Identificador:** PF-05
- **Épica origen:** E5 — Inscripciones y control de cupos
- **Requisitos asociados:** RF-14, CA-03, RN-04, RN-06, RN-18
- **Responsable:** Integrante B
- **Herramienta utilizada:** Cliente HTTP HTTPS (`TestClient` sobre `https://testserver` en `tests/test_inscripciones.py`), base de datos SQLite y vista web `/eventos/{id}`
- **Estado actual:** Ejecutada y aprobada en E5 (verificada con pruebas automatizadas y en interfaz web)

## Condiciones iniciales

1. Base de datos SQLite inicializada con las tablas `usuarios`, `eventos` e `inscripciones`.
2. Un evento en estado `publicado`, con `cupo_maximo = 10`, `fecha_inicio` y `fecha_limite_inscripcion` futuras en UTC, y público objetivo compatible (`todos` o acorde al rol).
3. Un usuario con rol `participante` (`CC 1000000101`, `activo = 1`) autenticado con cookie `pf04_session` válida.
4. Conexión servida sobre HTTPS con cabecera `Origin` confiable (`https://testserver` o `https://localhost:8000`).

## Casos cubiertos en E5

### Caso PF-05.1 — Inscripción exitosa de participante con cupo disponible (`CA-03`, `RF-14`)
- **Método / Ruta:** `POST /api/v1/eventos/{evento_id}/inscripciones`
- **Datos de entrada:** Identificador de evento publicado con cupos disponibles (`cupo_disponible > 0`). Cookie de participante autenticado.
- **Pasos:**
  1. Autenticarse como participante mediante `POST /api/v1/auth/login`.
  2. Consultar el detalle del evento en `GET /api/v1/catalogo/eventos/{id}` y verificar `cupos_disponibles == 10` e `inscripciones_activas == 0`.
  3. Enviar solicitud `POST /api/v1/eventos/{id}/inscripciones` con cabecera `Origin` válida.
  4. Inspeccionar la respuesta JSON y el registro creado en la tabla `inscripciones`.
  5. Consultar nuevamente el catálogo para validar la deducción del cupo disponible.
- **Resultado esperado:**
  - HTTP **201 Created** con esquema `InscripcionSalida`: `estado == "activa"`, `participante_id` del usuario en sesión, `evento_id` correspondiente y `creado_en` con zona horaria UTC.
  - La tabla `inscripciones` contiene exactamente 1 registro para la pareja `(evento_id, participante_id)`.
  - La consulta posterior a `GET /api/v1/catalogo/eventos/{id}` reporta `inscripciones_activas == 1` y `cupos_disponibles == 9`.
- **Resultado obtenido:** HTTP **201 Created**, persistencia confirmada en SQLite y cupo disponible recalculado en 9 (`tests/test_inscripciones.py::test_inscripcion_exitosa_reduce_cupo`).
- **Estado:** Aprobada.

### Caso PF-05.2 — Reinscripción permitida tras cancelación previa (`RN-06`, `RN-16`)
- **Método / Ruta:** `POST /api/v1/eventos/{evento_id}/inscripciones`
- **Datos de entrada:** Participante que previamente canceló su inscripción en un evento que todavía cuenta con cupos y plazo abierto.
- **Pasos:**
  1. El participante cancela su inscripción activa previa (`PATCH /api/v1/inscripciones/{id}/cancelar`).
  2. El participante solicita una nueva inscripción al mismo evento (`POST /api/v1/eventos/{id}/inscripciones`).
  3. Verificar registros en base de datos.
- **Resultado esperado:**
  - HTTP **201 Created**. Se genera un **nuevo registro** en la tabla `inscripciones` con `id` distinto, `estado == "activa"` y nueva marca temporal.
  - El registro anterior se conserva inalterado con `estado == "cancelada"` y `cancelada_en != NULL` (preservación de auditoría e historial).
- **Resultado obtenido:** HTTP **201 Created**, nuevo ID generado y presencia de 2 filas en BD (1 cancelada, 1 activa) (`tests/test_inscripciones.py::test_reinscripcion_tras_cancelar_crea_nuevo_registro`).
- **Estado:** Aprobada.

### Caso PF-05.3 — Consulta de inscripciones propias del participante (`RF-17`)
- **Método / Ruta:** `GET /api/v1/inscripciones/mias` y vista web `/mis-inscripciones`
- **Datos de entrada:** Sesión activa de participante con inscripciones activas e históricas.
- **Pasos:**
  1. Invocar `GET /api/v1/inscripciones/mias`.
  2. Verificar listado cronológico y datos del evento asociado.
- **Resultado esperado:** HTTP **200 OK** con lista de inscripciones del usuario, incluyendo `id`, `estado`, `titulo_evento`, `fecha_inicio_evento` y `estado_evento`.
- **Resultado obtenido:** HTTP **200 OK** con el listado estructurado de inscripciones del participante autenticado (`tests/test_inscripciones.py::test_listar_mis_inscripciones_retorna_historial`).
- **Estado:** Aprobada.
