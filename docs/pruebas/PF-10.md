# Prueba Funcional PF-10 — Registro y corrección de asistencia en ventana de 48 horas

- **Identificador:** PF-10
- **Épica origen:** E6 — Registro y consulta de asistencia
- **Requisitos asociados:** RF-20, RF-21, RF-22, RF-23, CA-05, RN-08, RN-10, RN-17
- **Responsable:** Integrante B (documentación en E8-B)
- **Herramienta utilizada:** Cliente HTTP HTTPS (`TestClient` sobre `https://testserver` en `tests/test_asistencia.py`), base de datos SQLite y vista web `/eventos/{id}/asistencia`
- **Estado actual:** Ejecutada y aprobada en E6 (verificada con pruebas automatizadas completas)

## Condiciones iniciales

1. Base de datos SQLite inicializada con las tablas `eventos`, `inscripciones` y `asistencias`.
2. Un evento publicado con inscripciones en estado `activa`.
3. Usuario organizador propietario del evento autenticado con cookie `pf04_session` y cabecera `Origin` confiable.
4. Fechas del evento configuradas para probar la ventana oficial: `fecha_inicio <= ahora_utc() <= fecha_fin + 48 horas`.

## Casos cubiertos en E6

### Caso PF-10.1 — Registro inicial de asistencia en ventana válida (`RF-20`, `CA-05`, `RN-08`)
- **Método / Ruta:** `PUT /api/v1/eventos/{evento_id}/inscripciones/{inscripcion_id}/asistencia`
- **Datos de entrada:** Cuerpo JSON `{"estado": "presente"}` (o `"ausente"`). Identificador de inscripción activa perteneciente a evento propio.
- **Condición temporal:** Evaluación en instante `t1` dentro de la ventana de asistencia oficial.
- **Pasos:**
  1. Enviar solicitud `PUT` con estado `"ausente"`.
  2. Verificar respuesta HTTP y consulta a la tabla `asistencias`.
- **Resultado esperado:**
  - HTTP **200 OK** con esquema `AsistenciaSalida`: `estado == "ausente"`, `registrado_por_id == organizador.id`, `registrado_en == t1` en UTC y `actualizado_en == None`.
  - Se crea exactamente 1 fila en la tabla `asistencias` vinculada a la `inscripcion_id`.
- **Resultado obtenido:** HTTP **200 OK**, persistencia en SQLite y campos de auditoría confirmados en `tests/test_asistencia.py::test_servicio_registrar_y_corregir_asistencia_sin_duplicar`.
- **Estado:** Aprobada.

### Caso PF-10.2 — Corrección de asistencia sin duplicación (`UPSERT`) (`RF-21`, `RN-17`)
- **Método / Ruta:** `PUT /api/v1/eventos/{evento_id}/inscripciones/{inscripcion_id}/asistencia`
- **Datos de entrada:** Solicitud posterior en instante `t2 > t1` cambiando el estado a `"presente"`.
- **Pasos:**
  1. Reenviar solicitud sobre la misma inscripción con `{"estado": "presente"}`.
  2. Verificar registros en base de datos.
- **Resultado esperado:**
  - HTTP **200 OK** con `estado == "presente"`, conservando `registrado_en == t1` y actualizando `actualizado_en == t2` con `actualizado_por_id == organizador.id`.
  - La tabla `asistencias` mantiene exactamente **1 fila** para esa inscripción (no duplica registros).
- **Resultado obtenido:** HTTP **200 OK**, ID conservado y conteo `SELECT COUNT(*) WHERE inscripcion_id = ?` igual a 1 (`tests/test_asistencia.py::test_servicio_registrar_y_corregir_asistencia_sin_duplicar`).
- **Estado:** Aprobada.

### Caso PF-10.3 — Rechazo fuera de la ventana de 48 horas (`RN-08`, `RF-23`)
- **Método / Ruta:** `PUT /api/v1/eventos/{evento_id}/inscripciones/{inscripcion_id}/asistencia`
- **Condiciones temporales probadas:**
  1. Antes del inicio del evento (`ahora_utc() < fecha_inicio`).
  2. Después de 48 horas de finalizado el evento (`ahora_utc() > fecha_fin + 48h`).
- **Resultado esperado:** HTTP **409 Conflict** con:
  ```json
  {
    "error": {
      "codigo": "ASISTENCIA_NO_PERMITIDA",
      "mensaje": "La asistencia solo puede registrarse desde el inicio del evento hasta 48 horas después de su finalización.",
      "detalles": []
    }
  }
  ```
  La operación es rechazada y no se altera la base de datos.
- **Resultado obtenido:** HTTP **409 `ASISTENCIA_NO_PERMITIDA`** verificado en `tests/test_asistencia.py::test_servicio_rechaza_fuera_de_ventana_48h`.
- **Estado:** Aprobada.

### Caso PF-10.4 — Rechazo por evento o inscripción no activa
- **Método / Ruta:** `PUT /api/v1/eventos/{evento_id}/inscripciones/{inscripcion_id}/asistencia`
- **Datos de entrada:** Evento en estado `cancelado` o inscripción con `estado == "cancelada"`.
- **Resultado esperado:** HTTP **409 Conflict** (`ASISTENCIA_NO_PERMITIDA`) garantizando que solo participantes con cupo activo registren asistencia.
- **Resultado obtenido:** HTTP **409** verificado en `tests/test_asistencia.py::test_servicio_rechaza_evento_o_inscripcion_cancelada`.
- **Estado:** Aprobada.

### Caso PF-10.5 — Control de acceso por rol y propiedad (`RN-10`)
- **Método / Ruta:** `PUT /api/v1/eventos/{evento_id}/inscripciones/{inscripcion_id}/asistencia`
- **Datos de entrada:** Solicitud ejecutada por organizador ajeno, participante o coordinación.
- **Resultado esperado:** HTTP **403 Forbidden** con `error.codigo == "SIN_PERMISO"`. Solo el organizador creador del evento puede mutar asistencias.
- **Resultado obtenido:** HTTP **403 `SIN_PERMISO`** confirmado en `tests/test_asistencia.py::test_api_rechaza_evento_no_iniciado_y_organizador_ajeno`.
- **Estado:** Aprobada.

### Caso PF-10.6 — Consulta de nómina con privacidad diferencial (`RF-22`, `RN-19`)
- **Método / Ruta:** `GET /api/v1/eventos/{evento_id}/asistencia`
- **Resultados verificados:**
  - Organizador propietario: visualiza el número de documento completo (`CC 1000000101`).
  - Coordinación: visualiza el número de documento enmascarado (`••••0101`).
- **Resultado obtenido:** HTTP **200 OK** con privacidad diferencial verificada en `tests/test_asistencia.py::test_servicio_permisos_y_privacidad_diferencial`.
- **Estado:** Aprobada.
