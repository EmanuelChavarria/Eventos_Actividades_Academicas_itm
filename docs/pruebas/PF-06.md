# Prueba Funcional PF-06 — Rechazo de inscripción por reglas de negocio

- **Identificador:** PF-06
- **Épica origen:** E5 — Inscripciones y control de cupos
- **Requisitos asociados:** RF-15, RF-16, CA-04, RNF-02, RNF-07, RNF-08, RN-04, RN-05, RN-06, RN-11, RN-15
- **Responsable:** Integrante B
- **Herramienta utilizada:** Cliente HTTP HTTPS (`TestClient` sobre `https://testserver` en `tests/test_inscripciones.py`), base de datos SQLite y Swagger `/docs`
- **Estado actual:** Ejecutada y aprobada en E5 (verificada con pruebas automatizadas completas)

## Condiciones iniciales

1. Base de datos SQLite inicializada con restricciones de integridad y tabla de inscripciones con índice único parcial `ux_inscripciones_activa`.
2. Varios eventos creados en la base de datos para simular cada condición de rechazo:
   - Evento con cupo lleno (`inscripciones_activas == cupo_maximo`).
   - Evento con fecha límite de inscripción expirada (`ahora_utc() > fecha_limite_inscripcion`).
   - Eventos en estados no publicados (`borrador` y `cancelado`).
   - Evento con público objetivo restringido (`docentes` exclusivamente).

## Casos cubiertos en E5

### Caso PF-06.1 — Rechazo por cupo agotado (`RN-05`, `CA-04`)
- **Método / Ruta:** `POST /api/v1/eventos/{evento_id}/inscripciones`
- **Datos de entrada:** Evento publicado con `cupo_maximo = 2` y 2 inscripciones activas previas. Petición de un tercer participante distinto.
- **Resultado esperado:** HTTP **409 Conflict** con cuerpo uniforme:
  ```json
  {
    "error": {
      "codigo": "CUPO_AGOTADO",
      "mensaje": "El evento ha alcanzado su capacidad máxima de inscripciones.",
      "detalles": []
    }
  }
  ```
  La tabla `inscripciones` mantiene únicamente 2 registros. No se produce sobrecupo.
- **Resultado obtenido:** HTTP **409 `CUPO_AGOTADO`** verificado en `tests/test_inscripciones.py::test_rechazo_cupo_agotado_retorna_409`.
- **Estado:** Aprobada.

### Caso PF-06.2 — Rechazo por inscripción duplicada activa (`RN-04`)
- **Método / Ruta:** `POST /api/v1/eventos/{evento_id}/inscripciones`
- **Datos de entrada:** Participante que ya cuenta con una inscripción en estado `activa` en el mismo evento.
- **Resultado esperado:** HTTP **409 Conflict** con `error.codigo == "INSCRIPCION_DUPLICADA"` y mensaje explicativo claro.
- **Resultado obtenido:** HTTP **409 `INSCRIPCION_DUPLICADA`** verificado en `tests/test_inscripciones.py::test_rechazo_inscripcion_duplicada_activa`.
- **Estado:** Aprobada.

### Caso PF-06.3 — Rechazo por evento no publicado (`RN-06`)
- **Método / Ruta:** `POST /api/v1/eventos/{evento_id}/inscripciones`
- **Datos de entrada:** Evento en estado `borrador` y evento en estado `cancelado`.
- **Resultado esperado:** HTTP **409 Conflict** con `error.codigo == "EVENTO_NO_PUBLICADO"`. No se permite registrar inscripciones en eventos que no estén en `publicado`.
- **Resultado obtenido:** HTTP **409 `EVENTO_NO_PUBLICADO`** verificado en `tests/test_inscripciones.py::test_rechazo_evento_no_publicado`.
- **Estado:** Aprobada.

### Caso PF-06.4 — Rechazo por inscripciones cerradas por fecha límite (`RN-15`)
- **Método / Ruta:** `POST /api/v1/eventos/{evento_id}/inscripciones`
- **Datos de entrada:** Evento publicado con `fecha_limite_inscripcion` en el pasado respecto a la hora UTC de evaluación.
- **Resultado esperado:** HTTP **409 Conflict** con `error.codigo == "INSCRIPCIONES_CERRADAS"`.
- **Resultado obtenido:** HTTP **409 `INSCRIPCIONES_CERRADAS`** verificado en `tests/test_inscripciones.py::test_rechazo_fecha_limite_vencida`.
- **Estado:** Aprobada.

### Caso PF-06.5 — Rechazo por incompatibilidad con público objetivo (`RN-11`)
- **Método / Ruta:** `POST /api/v1/eventos/{evento_id}/inscripciones`
- **Datos de entrada:** Evento con `publico_objetivo == "docentes"`. Participante autenticado con `tipo_participante == "estudiante"`.
- **Resultado esperado:** HTTP **409 Conflict** con `error.codigo == "PUBLICO_NO_PERMITIDO"`.
- **Resultado obtenido:** HTTP **409 `PUBLICO_NO_PERMITIDO`** verificado en `tests/test_inscripciones.py::test_rechazo_publico_objetivo_incompatible`.
- **Estado:** Aprobada.

### Caso PF-06.6 — Rechazo por evento inexistente
- **Método / Ruta:** `POST /api/v1/eventos/999999/inscripciones`
- **Datos de entrada:** ID de evento inexistente en base de datos.
- **Resultado esperado:** HTTP **404 Not Found** con `error.codigo == "EVENTO_NO_ENCONTRADO"`.
- **Resultado obtenido:** HTTP **404 `EVENTO_NO_ENCONTRADO`** verificado en `tests/test_inscripciones.py::test_rechazo_evento_inexistente_retorna_404`.
- **Estado:** Aprobada.

### Caso PF-06.7 — Integridad transaccional y rechazo atómico (`RF-16`)
- **Verificación:** En ninguno de los casos anteriores se crearon registros parciales o huérfanos en SQLite, y los cálculos de disponibilidad en catálogo se mantuvieron intactos.
